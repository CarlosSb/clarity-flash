# Migração do Backend Go para Fiber: Estudo de Viabilidade

## Objetivo
Migrar o backend do ClarityFlash de `net/http` para Fiber v3, visando maior performance, limpeza da codebase e facilidade de manutenção, enquanto mantém compatibilidade com funcionalidades existentes (WebSocket via gorilla, PostgreSQL, etc.).

## Estado Atual da Codebase

### Arquitetura Atual
- **Framework**: Go padrão `net/http`
- **Roteamento**: `http.NewServeMux()` com `HandleFunc`
- **Handlers**: Padrão `http.HandlerFunc` com `(w http.ResponseWriter, r *http.Request)`
- **Middleware**: Encadeamento manual com `func(next http.Handler) http.Handler`
- **Estrutura**: Clean Architecture com handlers, services, repositories
- **Dependências Externas**: gorilla/websocket (WebSocket), PostgreSQL (lib/pq)

### Principais Arquivos a Migrar
- `internal/api/routes.go`: Configuração de rotas
- `internal/handler/*.go`: Handlers HTTP
- `internal/middleware/*.go`: Middleware de auth, CORS, JWT
- `internal/websocket/handler.go`: Handler WebSocket

## Benefícios da Migração para Fiber

### Performance
- **Throughput**: ~60% maior que `net/http` (130k vs 80k req/s em benchmarks)
- **Memória**: 30-50% menor uso (pooling agressivo)
- **Latência**: Melhor consistência sob carga alta
- **Conexões**: Melhor suporte a alta concorrência

### Developer Experience
- **API Express.js-like**: Familiar para devs full-stack
- **Sintaxe Limpa**: Menos boilerplate que `net/http`
- **Middleware**: Mais intuitivo e flexível
- **Debugging**: Melhor logging e error handling
- **Ferramentas**: CLI de migração oficial para v3

### Manutenibilidade
- **Código Mais Legível**: Menos verbosidade
- **Middleware Ecosystem**: Crescente e ativo
- **Updates**: Suporte ativo, v3 requer Go 1.25+
- **Type Safety**: Melhor com generics

## Trade-offs e Riscos

### Desvantagens
- **Compatibilidade**: Fasthttp vs net/http (sem HTTP/2, middleware lock-in)
- **Ecosystem**: Menor que Gin/Echo (mas crescendo)
- **Curva de Aprendizado**: API diferente de net/http padrão
- **Breaking Changes**: v2→v3 pode ter mudanças

### Riscos
- **WebSocket**: gorilla/websocket funciona, mas pode precisar ajustes
- **Middleware Existente**: Reescrita necessária
- **Testes**: Reescrita completa dos testes de integração
- **Performance Real**: Benefícios visíveis em carga alta, não em I/O-bound

## Plano de Migração

### Fase 1: Preparação (1-2 dias)
1. **Setup Fiber**: Adicionar `github.com/gofiber/fiber/v3` ao go.mod
2. **Estrutura Base**: Criar novo app Fiber em `internal/api/fiber_app.go`
3. **CLI Migração**: Usar Fiber Migration CLI para v3
4. **Testes Baseline**: Executar testes atuais para baseline

### Fase 2: Core Migration (3-5 dias)
1. **Roteamento**:
   - Substituir `http.NewServeMux()` por `fiber.New()`
   - Converter `mux.HandleFunc("GET /health", handler)` para `app.Get("/health", handler)`
   - Suporte a parâmetros dinâmicos: `:id` em vez de `{id}`

2. **Handlers**:
   - Converter `func(w http.ResponseWriter, r *http.Request)` para `func(c *fiber.Ctx) error`
   - Adaptar responses: `c.JSON()`, `c.SendString()` em vez de `json.NewEncoder(w)`
   - Context: `c.Locals("user_id")` em vez de `context.WithValue()`

3. **Middleware**:
   - Converter para `func(c *fiber.Ctx) error`
   - Auth: Adaptar JWT validation
   - CORS: Usar middleware Fiber nativo

### Fase 3: Integrações Especiais (2-3 dias)
1. **WebSocket**: Verificar compatibilidade com gorilla/websocket
2. **Streaming Upload**: Adaptar file upload handlers
3. **Database**: Sem mudanças (PostgreSQL via lib/pq)
4. **Auth**: Migrar JWT handling

### Fase 4: Testes e Otimização (2-3 dias)
1. **Unit Tests**: Atualizar para Fiber context
2. **Integration Tests**: Reescrita completa
3. **Performance Tests**: Benchmark com wrk/vegeta
4. **Memory Profiling**: Verificar reduções

### Fase 5: Deployment (1 dia)
1. **Build**: Testar compilação
2. **Config**: Ajustar env vars se necessário
3. **Rollback Plan**: Manter net/http como fallback
4. **Monitoring**: Setup métricas de performance

## Estimativa de Esforço
- **Total**: 8-14 dias de desenvolvimento
- **Por Arquivo**: ~2-4 horas cada handler/middleware
- **Testes**: +50% do tempo total
- **Equipe**: 1-2 devs Go experientes

## Recomendações

### Quando Migrar
- ✅ Se performance é bottleneck atual
- ✅ Equipe tem experiência com Express.js/Node
- ✅ Aplicação CPU-bound (não I/O-bound)
- ✅ Quer reduzir complexidade de roteamento

### Alternativas Considerar
- **Gin**: Mais maduro, similar performance, net/http compatível
- **Echo**: Feature-rich, bom meio-termo
- **Permanecer**: Se mudanças não justificam esforço

### Estratégia de Migração
1. **Piloto**: Migrar endpoints não-críticos primeiro
2. **Feature Flags**: Executar ambas versões em paralelo
3. **Gradual**: Migrar módulo por módulo
4. **A/B Testing**: Comparar performance real

## Conclusão
A migração para Fiber oferece ganhos significativos em performance e DX, tornando o código mais limpo e fácil de manter. O esforço é substancial mas justificável para um projeto em crescimento. Recomendo proceder com análise de performance atual antes de decidir.
